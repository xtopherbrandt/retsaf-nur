# Section 4 — Physiological State Model

*Build-ready specification, Phase 2. This section defines the layer that sits between the derived metrics (Section 3) and everything that consumes an estimate of the athlete — the pace target (Section 1), plan generation (Section 5), and the adaptation logic (Section 6). It is the system's **owned alternative to a vendor VO₂max number**: instead of trusting an undocumented estimate, the system maintains its own transparent profile of the physiological determinants of race pace — critical speed and D′, velocity at VO₂max, functional threshold pace, a running-economy proxy, durability, and the individual endurance exponent — each carrying a trend and a confidence, each estimated by a stated method from the raw-derived metrics Section 3 produces. It conforms to `research/00` as the decision authority — the raw-over-derived principle and its owned-open-method carve-out (`research/00` PRIN-07, PRIN-09), the individualization governing rule (`research/00` IND-01), the resolved cold-start decision (`research/00` COLD-01), and the load-bearing findings that the system owns its state model (`research/00` ARCH-02) and that every determinant carries a confidence, low confidence widening the guardrails (`research/00` ARCH-08, ARCH-11) — and cites `research/05` §3 and `research/01` §4.1–§4.3, §1.6 for the models and derivations behind every estimator it states. Per the project conventions, every method is stated here in full; the evidence behind it lives in the cited docs and is not re-argued. Every numeric constant below is a **heuristic default** (`research/00` DOC-06), tunable per athlete only under the individualization rule (`research/00` IND-01) and never where it is a design invariant.*

## 4.1 What this section owns, and the boundaries it respects

Section 4 maintains the **physiological state model**: the athlete's estimated current profile of the determinants of race pace, together with a short- and long-term trend and a confidence for each determinant (`research/00` ARCH-02; `research/05` §3). It is the system's memory — the shared, slowly-varying object that makes adaptation cumulative rather than reactive, so that a good block of training moves a durable estimate rather than only nudging a daily gate. Three boundaries fix what this section is and is not.

- **Section 4 estimates state, not metrics.** Section 3 computed per-session and rolling *metrics* — a load number, a fitness/fatigue/form triple, a decoupling percentage, an HRV verdict, a durability drift figure — each a transparent function of raw streams (§3.10). Section 4 turns those metrics, and the athlete's maximal-effort history, into *state*: point estimates of the athlete's determinants. It does not re-derive any metric; it consumes Section 3's outputs as inputs and adds the inferential step Section 3 deliberately withheld (Section 3 flags a candidate response trend, §3.6.4; Section 4 decides whether the corroboration bar is met and moves the determinant).
- **The interface with Section 3 is two-way and load-bearing.** Section 4 reads Section 3's metrics; Section 3's load formulas in turn read three anchors this section owns — **functional threshold pace, HR_rest, and HR_max** (§3.1, §3.4.1). Those anchors originate as athlete-profile inputs (Section 1 §1.3 supplies `resting_hr_bpm` and `max_hr_bpm`, `resting_hr_bpm` from the latest stored FIT file that carries it and `max_hr_bpm` from the latest stored running FIT file that carries it, each else the athlete's entry, with no age-based default) and are refined here as history accrues; Section 4 publishes the current best estimate of each, and Section 3 records which value it used, so a metric other than HR-TRIMP can be recomputed when the estimate updates. HR-TRIMP is the exception, for the HR settings only: per field it uses the value the session's own file carried, else the setting in effect on the run's date (the latest stored file that started at or before the run's start, a running file for HR_max and threshold HR, or the latest dated HR entry effective on or before the run's local date, whichever has the later local date, the file winning when both share it; with none, today's anchor, flagged out of period when that anchor came from a later file; sex is today's anchor), saved with the load and never moved by a later anchor or entry until the athlete recomputes that load (F021); this departs from the current-estimate rule (section 3.1 records the same departure), and threshold pace is untouched by it. Threshold pace especially is re-anchored continuously, which is why a stale threshold biasing every rTSS (Section 3's stated garbage-in risk, §3.5.4) is Section 4's responsibility to prevent.
- **Section 4 produces the estimate Section 1 consumes, but does not compute the pace target.** Section 1 §1.4 turns a state estimate into an expected average race pace; the anchors that procedure consumes at its Stage 1 — CS, D′, vVO₂max, the individual endurance exponent `b`, the economy modifier, and the durability estimate — are exactly the determinants this section owns and defines below (§4.2). Section 1 §1.4.4 also reads a modeled *acclimatization state* for its altitude modifier; this section does not yet carry an explicit acclimatization determinant and, like Section 1, defaults to the conservative no-acclimatization assumption — the gap is logged as an open item (§4.7) rather than claimed as owned here. Section 4 supplies the *athlete*; Section 1 supplies the *race translation*. Neither performs the other's step. Likewise Section 4 supplies the determinant profile that lets the gap-to-goal be decomposed by determinant, but the decomposition-driven periodization choice belongs to Section 5 and the projection to Section 1 (`research/05` §4).

Everything in this section is built only from raw-derived inputs — Section 3's metrics and the athlete's own maximal efforts — never from the quarantined vendor sidecar (§2.3.6, `research/00` PRIN-08). Where the state model reproduces a documented open method that is itself an estimate — most importantly the non-exercise cold-start seed (§4.4.2) — that method is **owned and transparent**: its formula is stated in full below, so it lives in the owned namespace and is consistent with raw-over-derived, exactly as `research/00` PRIN-09 and COLD-10 provide.

## 4.2 The determinant profile

The state model is a structured object holding one record per determinant. Each record carries a **point estimate** (in the determinant's natural units), a **short-term trend** and a **long-term trend** (direction and rate of change over recent weeks and over the training block), a **confidence** (§4.3), and a **provenance** stamp recording which efforts or metrics produced the current estimate and when. The determinants below are the six `research/00` ARCH-02 names, plus the two heart-rate anchors the profile must publish for Section 3. They are estimated in dependency order: the velocity anchors (CS/D′, vVO₂max, threshold pace) come from maximal-effort performance data, threshold pace also from the submaximal threshold workouts the athlete tags or names (section 4.3.4); the economy, durability, and endurance-exponent records are refinements that shape how those anchors project to a race.

### 4.2.1 Critical speed (CS) and D′

Critical speed is the single most useful anchor for threshold-to-10K pace — the asymptote of the speed–time-to-exhaustion relationship, the highest speed sustainable in a metabolic steady state — and D′ is the finite distance (energy) capacity usable above it (`research/01` §4.2; `research/05` §3.1). Both are fitted from the athlete's best sustained efforts across a spread of durations, using the linear distance–time form of the two-parameter model:

> **distance = CS · t + D′**

Given a set of qualifying maximal efforts, each a (time `t`, distance `d`) pair, CS is the **slope** and D′ the **intercept** of the ordinary-least-squares line of distance on time. The efforts are drawn from races, time trials, and hard workout segments the athlete actually completed, spanning roughly **2–20 minutes** — the duration band over which the linear model is well-behaved (`research/05` §3.1; `research/01` §4.2 gives the model and its ~30–60 min steady-state anchor horizon). Qualifying efforts must be genuinely maximal or near-maximal for their duration and must span **at least two well-separated durations** for the fit to be identifiable; the estimator prefers three or more across the band, because a two-point fit has no residual to gauge its own quality against. CS is re-fitted whenever a new qualifying maximal effort arrives (a race, a time trial, or a workout segment the completion-vs-prescription feature marks as a maximal effort, §3.2).

Two limitations `research/01` §4.2 states are carried into the estimate and must not be lost downstream: CS is treated as a fixed boundary by the model but **itself drifts down over prolonged exercise** (this is precisely the durability phenomenon, §4.2.5), so CS anchors short-to-middle events accurately and the marathon only as a drifting upper bound; and the fit is **sensitive to the choice and quality of the test efforts**, so the confidence on CS/D′ (§4.3) is driven directly by how many qualifying efforts exist, how well they span the duration band, and their stream quality.

### 4.2.2 Velocity at VO₂max (vVO₂max)

Velocity at VO₂max — the running velocity that folds VO₂max and economy into a single speed — is the practical anchor for 3K–10K prescription and a cross-check on the short end of the CS fit (`research/01` §4.1; `research/05` §3.1). It is estimated from **short maximal efforts of roughly 3–8 minutes' duration** (the time-to-exhaustion band at vVO₂max), taken as the sustained velocity of such an effort, and is cross-checked against the CS fit, from which the severe-domain velocities can be predicted. When both a direct short-effort estimate and the CS-model prediction are available, the profile carries the direct estimate as the point value and uses their agreement as a confidence signal; a large disagreement lowers confidence on both and flags the effort set for review rather than silently averaging.

### 4.2.3 Functional threshold pace

Functional threshold pace is the pace at the lactate-turnpoint (LT2) anchor — the reference intensity the whole zone system and Section 3's rTSS are built on (`research/01` §1.3, §3.1; `research/04` §4.1). It is the `FTP_pace` Section 3's rTSS and intensity-factor formulas consume (§3.4.1), and the anchor Section 5's relative-anchored paces are stored against (`research/00` ARCH-04). Section 4 estimates it two ways and reconciles them:

- from the athlete's **best sustained tempo/threshold efforts of roughly 20–60 minutes** (the duration band in which effort is threshold-anchored; `research/05` §3.1, with the LT2/MLSS physiology in `research/01` §1.3), taken as the sustainable pace of such an effort; and
- from the **CS fit** (§4.2.1), since CS closely approximates the LT2/MLSS boundary and predicts the threshold pace directly (`research/01` §1.3).

When both exist the estimator blends them by confidence (§4.3); when only one exists it is used with correspondingly lower confidence. Threshold pace is the determinant the individualization rule (§4.5) singles out as **continuously re-anchored**, because it is readily identifiable from ordinary training and racing and because Section 3's entire load chart depends on it being current. Every re-anchoring is published to Section 3 with a version stamp so any rTSS computed against a superseded threshold can be recomputed. As built, threshold pace is estimated from tagged or named efforts only (section 4.3.4): the races and time trials the athlete marks Race in Garmin Connect, and the threshold workouts the athlete marks Training or whose workout name is on the configured list, read over their sustained work reps; it is unpopulated before the first qualifying one (IDEA-161), and the CS-derived estimate and the blend by confidence wait for the CS constants (IDEA-157).

### 4.2.4 Running-economy / efficiency proxy

The system has no laboratory VO₂ measurement, so running economy is carried as a **within-athlete efficiency proxy**, not an absolute cost (`research/01` §1.4; `research/05` §3.1). The proxy is the **efficiency-factor (EF) trend at a controlled reference effort** that Section 3 computes (§3.6.2): grade-adjusted speed per unit heart rate on a steady aerobic segment, interpreted only as a within-athlete trend under matched conditions. Section 4 records the current EF level and its trend as the economy determinant. Two constraints from Section 3 and `research/01` are preserved: **the absolute value is never claimed or compared across athletes** — only the athlete's own trend is interpreted — and a favorable trend is credited as improving economy only after the multi-week corroboration bar of §3.6.4 is met (economy adapts slowly, over months, so a durable EF rise is exactly the expected signature; `research/01` §2.3). The economy determinant feeds Section 1 §1.4.3's economy modifier: where the state model has no basis to distinguish race-day economy from the economy embedded in the CS/vVO₂max anchors, the modifier is 1.0, and the equipment (super-shoe) adjustment Section 1 applies is separate from this within-athlete trend.

### 4.2.5 Durability

Durability — resistance to the deterioration of economy, thresholds, and the pace–HR relationship over prolonged exercise — is the determinant most responsible for late-race slowdown, above all in the marathon, and is an explicitly **emerging** construct (`research/01` §1.6; `research/00` REG-06, the durability row). Section 4 carries a durability determinant fed by Section 3's within-athlete durability-drift metric (§3.8): the drift in EF/decoupling over the back third of long runs at equal grade-adjusted pace, trended over weeks. The determinant is used under the three constraints Section 3 and `research/01` impose: **within-athlete trend only** (the absolute drift scale is uncalibrated across athletes), **corroborating not primary** (its influence on the race-pace projection is bounded and surfaced in the confidence band rather than presented as precise), and **flagged emerging** everywhere it surfaces. It feeds Section 1 §1.4.3's duration-dependent durability decay — larger for the marathon, negligible for the 5K — and, because CS itself drifts over prolonged exercise (§4.2.1), it is the determinant that tells the projection how far below the fresh-state CS the marathon is actually run.

### 4.2.6 Individual endurance exponent (Riegel *b*)

The endurance exponent governs how sustainable pace falls as race duration rises, and is the determinant that projects a short anchor to a long race (`research/01` §4.3; `research/05` §3.1). It is fitted to the athlete's own duration–performance data via the Riegel power law:

> **T₂ = T₁ · (D₂ / D₁)^b**

where `b ≈ 1.0` would mean pace is held perfectly across distances and `b > 1` encodes the real slowdown. Section 4 fits `b` from the athlete's qualifying maximal efforts and races spanning a spread of distances (from `history` and `known_bests`, §1.3), by regressing log-time on log-distance across those efforts — the slope of that line is the individual `b`. The exponent is equivalently expressible as the athlete's fractional-utilization curve (the sustainable %vVO₂max/%CS as a function of race duration: ~95–100% at 5K falling to ~75–85% at the marathon; `research/01` §1.5, §4.3), and the two representations are kept consistent. Per the individualization rule (§4.5) and the endurance-exponent register row, the **individual `b` is used only when enough quality efforts across a spread of distances identify it above the noise**; otherwise the profile holds the **population default `b = 1.06`** (`research/01` §4.3) with a correspondingly widened confidence interval. The caveat `research/01` §4.3 states is carried: `b` is individual and trainable — durability and long-run volume flatten it — and extrapolating far (e.g. projecting a marathon from only a 5K anchor) systematically under-predicts the longer time, so a wide extrapolation is flagged low-confidence and Section 1 §1.4.2 prefers an anchor close in duration to the goal race. This is the same exponent Section 1 §1.4.2 consumes; Section 4 owns its estimate and Section 1 owns its application to the goal distance. Dated note 2026-10-24 (F029): as built, `b` is fitted from the races the athlete tags Race in Garmin Connect, not mined from history or `known_bests`: the weighted least-squares slope of log time on log GAP-equivalent distance over the tagged races of the last 1095 days, each faded over the last 182 days of that window, after a fitness-drop screen that leaves out a race run while fitness had fallen more than 30 % in the four weeks before it; with no filter step; individual when at least three races, a fading race counted by its weight (2026-10-28), span a twofold distance ratio, else the population 1.06 with error 0.05 (section 4.3.5, REG-32).

### 4.2.7 The published heart-rate anchors: HR_rest and HR_max

Beyond the six determinants, the profile publishes two heart-rate anchors that Section 3's HR-TRIMP and heart-rate-reserve formulas require (§3.4.1) and that the readiness layer's resting-HR baseline uses (§3.7.4). **HR_rest** is seeded from the athlete profile's `resting_hr_bpm` (§1.3) and refined from the resting/overnight chest-strap captures (§2.4.5, §3.7): the estimator tracks the athlete's true resting heart rate as a slowly-varying baseline, distinct from the day-to-day resting-HR deviation Section 3 trends for readiness. **HR_max** is seeded from the athlete profile's `max_hr_bpm` (section 1.3): the Garmin setting in the latest stored running FIT file that carries it, else the athlete's entered value, else unavailable (`research/00` PRIN-28 admits the setting as a profile input). Unlike an estimate revised upward only, the seed follows the latest file, and Garmin's setting can go down as well as up: the corpus's FR945 Run files read 188, then 189, then 188, so a lower latest-file value replaces a higher earlier one. No age-based prior seeds HR_max, because no formula for one is specified (IDEA-138 owns it); with no file value and no entry, HR_max is unavailable rather than estimated from age. Where the estimator refines the seed, a genuinely maximal effort that records a higher heart rate than the current estimate raises it, whereas a low observed max on an easy day is not evidence the true max fell. Both anchors carry a confidence like any determinant, and both are published to Section 3 with the same version-stamped interface as threshold pace. A TRIMP is not recomputed when an anchor moves: HR-TRIMP uses, per field, the value the session's own file carried, else the setting in effect on the run's date (the latest stored file that started at or before the run's start, a running file for HR_max and threshold HR, or the latest dated HR entry effective on or before the run's local date, whichever has the later local date, the file winning when both share it; with none, today's anchor, flagged out of period when that anchor came from a later file), saved with the load together with its source and, where an anchor supplied it, the anchor version; this departs from the current-estimate rule for the HR settings only (section 3.1), and a saved load is corrected by entering the dated setting and recomputing it (`POST /sessions/{id}/load/recompute`, F021).

## 4.3 Trend and confidence: the estimator

Each determinant is modeled as a **slowly-varying quantity** observed noisily through the athlete's efforts and metrics, and is updated by a transparent recursive estimator rather than by overwriting the estimate with each new observation (`research/05` §3.3). The construction is stated in full here so an implementer needs no further lookup.

### 4.3.1 The recursive update

Treat each determinant's true value as drifting slowly over time, and each qualifying observation (a fitted CS from a new effort set, a threshold pace from a tempo effort, an EF level, a durability-drift figure) as a noisy measurement of it. Each determinant carries, alongside its point estimate, an **estimate variance P** — the smaller the variance, the higher the confidence — and each observation arrives with a **measurement variance R** that is smaller the higher the observation's quality (a clean, chest-strap, 1 Hz, well-spanned maximal effort has small R; a marginal or thin-data observation has large R). The estimate is updated by the standard **scalar Kalman filter**: the new estimate is the prior estimate pulled toward the new observation by a **gain K between 0 and 1**,

> **K = P / (P + R)** ,  **estimate_new = estimate_prior + K · (observation − estimate_prior)** ,  **P_new = (1 − K) · P**

so the gain — and hence how far the estimate moves — **rises with the observation's quality** (smaller R) **and with the prior's own uncertainty** (larger P), and the update also *shrinks* the variance toward higher confidence. Before each update, the prior variance is **inflated for staleness** by a process-noise term proportional to the elapsed time since the determinant was last observed, **P ← P + Q·Δt**, so a determinant that has gone unobserved for weeks drifts back toward lower confidence (larger P) and therefore accepts the next good observation more readily. Concretely, a high-quality observation arriving against a stale, low-confidence prior pulls the estimate hard (K near 1); a marginal observation arriving against a fresh, high-confidence prior barely moves it (K near 0). This is the mechanism that makes the state model cumulative: a single session cannot swing a well-established estimate, but a sustained run of consistent observations will. The per-determinant defaults — the measurement-variance scale R as a function of the quality flags (effort count, duration/distance spread, stream cleanliness) and the process-noise rate Q — are shipped heuristics tunable per athlete only under the individualization rule (`research/00` IND-01, DOC-06); an implementer may start with R inversely proportional to the qualifying-effort count and quality weight and Q set so an unobserved determinant loses roughly half its confidence over a training block. The filter is scalar and per-determinant; the spec does not require a full multivariate Kalman filter, and the CS/D′ pair, though jointly fitted, is filtered as two coupled scalars sharing one observation event. Threshold pace simplifies the quality-dependent R to a single R for every qualifying race and threshold workout (section 4.3.4): the quality flags that matter for an effort exclude it outright rather than enlarging its R. Dated note 2026-10-24 (F029): the endurance exponent takes no filter step and no staleness inflation: it is a weighted least-squares fit over the tagged races of a 1095-day window, each race's weight falling to 0 over the window's last 182 days, recomputed on every read; the window and the fade are its staleness rule (section 4.3.5).

**Combining two concurrent observations.** Where two observations of the same determinant arrive together — a directly-measured vVO₂max and the CS-model prediction of it (§4.2.2), or a tempo-derived and a CS-derived threshold pace (§4.2.3) — they are combined by **inverse-variance (precision) weighting** before entering the filter: the combined observation is the R-weighted mean `(o₁/R₁ + o₂/R₂)/(1/R₁ + 1/R₂)` with combined variance `1/(1/R₁ + 1/R₂)`. Equivalently, feeding the two through the filter sequentially yields the same posterior; either order is acceptable. A large disagreement between the two (their difference exceeding what their variances predict) does not silently average — it inflates the combined variance and flags the effort set for review (§4.2.2), so a contradiction lowers confidence rather than hiding in a mean.

### 4.3.2 What confidence encodes, and how it moves

Confidence is the estimate variance P re-expressed for consumers, and it reflects **data recency, quantity, and quality** exactly because P is driven by them (`research/00` ARCH-08; `research/05` §3.3): P **shrinks** (confidence rises) with more, more-recent, higher-quality qualifying observations — more maximal efforts, better spread across the duration or distance band, cleaner streams — through the small-R updates of §4.3.1, and P **grows** (confidence decays) with staleness through the Q·Δt inflation, so an estimate built on efforts now months old loses confidence even if nothing has contradicted it, because the athlete has since trained or detrained. Confidence is surfaced two ways: as a **prediction interval** on the point estimate, computed as the point value ± z·√P for a chosen coverage z (this is the interval Section 1 §1.4.6 widens the pace-target confidence band from), and as a **qualitative low/medium/high label** — mapped from √P against determinant-specific default thresholds — for athlete-facing display. It is surfaced, never hidden as false precision (`research/00` ARCH-11): the athlete sees that an estimate is provisional, and the adaptation logic reads the same confidence to decide how conservative to be (§4.6). Threshold pace is filtered in log speed (section 4.3.4), so its interval, ± z·√P on the log of grade-adjusted speed, is symmetric in log speed and asymmetric when converted to pace, and its label compares P with R and 4R directly rather than √P with a threshold. Dated note 2026-10-24 (F029): the endurance exponent's confidence is the fit's own, not a filter's P: its interval is b ± t·se with Student's t at 0.90 for the whole part of n_eff − 2 degrees of freedom, n_eff being the races counted by their weights (2026-10-28; z past 30), or, below the bar, the population 1.06 ± z · 0.05, and its label compares se with 0.02 and 0.04 directly (section 4.3.5).

### 4.3.3 The corroboration gate on response-driven moves

A determinant is moved on the strength of a **training-response trend** (a falling decoupling, a rising EF, a downward HR-at-pace drift) only when Section 3's corroboration bar is met: a trend holding over roughly **≥ 2–3 weeks**, or a re-estimation supported by **≥ 2 qualifying efforts** (§3.6.4; `research/05` §2.2). Section 3 flags a candidate trend; Section 4 is where the decision to credit it is taken, and where the filter of §4.3.1 then applies the move at a gain set by the corroborating evidence's quality. A single hot session never re-anchors threshold or shifts CS (the "trends, not single readings" principle, which `research/00` PRIN-06 states for readiness signals, applied here); a genuine new maximal effort, by contrast, is a direct high-quality observation and updates the fitted determinants (CS/D′, vVO₂max, `b`) immediately through the filter, without waiting on the multi-week bar, because it is a measurement rather than a trend inference. The distinction is exactly the one Section 3 draws: re-anchoring from a maximal effort is measurement; crediting adaptation from a drifting EF is trend inference and must clear the bar. Dated note 2026-10-24 (F029): as built, `b` takes no filter step (section 4.3.5); a newly tagged race enters its fit at the next read of `GET /state`.

### 4.3.4 Threshold-pace constants (spec-introduced)

The estimator of sections 4.3.1 and 4.3.2 is applied to threshold pace with the constants below, ruled by the user on 2026-10-14. Each is a spec-introduced engineering default under `research/00` DOC-08, recorded in the register as REG-31. The observation is `y = ln(1000 / gap_avg_pace_s_per_km)`, the natural log of the effort's grade-adjusted speed in m/s, taken from each **qualifying effort**, of two kinds. A **race** is a running session the athlete tagged `race` (spec/05 section 5.2.6) whose duration (`timer_time_s`, else the summary `duration_s`) lies in 1200–3600 s inclusive (the reading of section 4.2.3's "roughly 20–60 minutes"), that carries neither `distance_regressed` nor `smart_recording` (checked in that order), and whose GAP pace is a finite number above zero. A **threshold workout** (ruled by the user on 2026-10-16 and 2026-10-18) is a running session the athlete admits in one of two ways: it is tagged `threshold_workout`, which the athlete marks Training in Garmin Connect (spec/02 section 2.7.3), or one of its workout steps carries a workout name listed in the API's `threshold_workout_names` (a listed name also takes a race-tagged session out of the races, so it is read once, as a workout). It is read over its **sustained work reps**: a work lap is a lap of intensity `active` or `interval` under a workout step of intensity `active` or `interval` that is not a repeat step and whose target is neither null nor open (spec/02 section 2.3.2); a rep is a maximal run of adjacent work laps sharing one step index, its length their summed timer times; a rep is sustained when it lasts at least `workout_min_rep_s`. It qualifies when, in this order, its laps have been read (else `laps_not_read`), its laps and steps read without raising (else `laps_unreadable`), every work lap's times read, a remainder lap under two seconds adding its time to its rep and no window (else `lap_times_unreadable`), it has a work lap (else `no_workout_steps`), it has a sustained rep (else `no_sustained_work`), it carries neither flag, each sustained rep's GAP pace is a finite number above zero (a rep whose pace is not is dropped; `gap_pace_unavailable` when none is left), a sustained rep **counts** when its GAP pace is no slower than `workout_rep_band` times the fastest sustained rep's (the fastest always counts), the counted reps' lengths total at least `workout_min_active_s`, with no maximum (else `active_time_below_minimum`), and its GAP pace over the counted reps is a finite number above zero: F013's counted segments whose start lies in a counted rep's lap window `[start_t, end_t)`. It enters the same filter with the same R, at its session start, with `y` from that GAP pace. The signal is the athlete's tag or name list, never pace alone: nothing infers a workout or a work rep from pace, and the band drops a slower rep only beside a faster one. Degraded GPS excludes no race or workout: it is a per-record fraction, never a session flag, and is shown for every effort used. A race with no altitude counts at its flat pace.

## 4.4 Establishing the starting state (cold start and warm start)

At program start the system has only the athlete profile and whatever historical raw data exists (§1.3). How it establishes day-one state depends on how much qualifying history is present. The procedure has a **warm-start** path (adequate history) and a **cold-start** path (thin or absent history), with a confidence-blended hand-off between them as running history accrues. This resolves and, per `research/00` COLD-07, **amends** the population-defaults-only cold start `research/05` §3.2 originally specified.

### 4.4.1 Warm start: mining an adequate history

When the athlete supplies enough qualifying history, the starting state is estimated directly from it (`research/05` §3.2):

1. **Ingest and gate all available history** (Section 2), building the grade-adjusted-pace and unified-load time series (Section 3). The chart-level cold start — seeding CTL/ATL by running the EWMAs forward over the historical load series so the athlete does not start at an artificial zero fitness — is **already handled by Section 3 §3.5.3** and is not repeated here; Section 4 owns the *physiological-determinant* starting state only.
2. **Mine maximal-effort segments** across durations — races, time trials, hard intervals identified from the completion-vs-prescription and descriptor features — and fit **CS/D′** (§4.2.1), **vVO₂max** (§4.2.2), and the **individual endurance exponent `b`** (§4.2.6). When fewer than the minimum qualifying efforts exist (efforts spanning at least two well-separated durations for CS; a spread of distances for `b`), the affected determinant falls back to its population default and is marked **low-confidence** rather than fitted to noise (§4.5). Threshold pace is not mined from this search: it reads only the efforts the athlete tags or names, as races or as threshold workouts (step 3). Dated note 2026-10-24 (F029): as built, `b` is not mined from this search either: it is fitted from the races the athlete tags Race, and is individual only when at least three races, counted by their weights (2026-10-28), span a twofold GAP-equivalent distance ratio; else the population 1.06 with error 0.05, `low` (section 4.3.5).
3. **Estimate threshold pace** from the best sustained tempo/threshold efforts and from the CS fit (§4.2.3). As built, threshold pace is estimated from tagged or named efforts only, of two kinds (section 4.3.4): the races and time trials the athlete marks Race in Garmin Connect, read whole, and the threshold workouts the athlete marks Training or whose workout name is on the configured list, read over their sustained work reps, at least 590 s of them in all; it is unpopulated before the first qualifying one (IDEA-161); the CS-derived estimate and the blend by confidence wait for the CS constants (IDEA-157).
4. **Establish the economy and durability baselines** from the EF and long-run-drift history where it exists (§4.2.4–§4.2.5), as within-athlete baselines only.
5. **Establish HR_rest, HR_max, and the HRV/wellness baselines** from the profile inputs and whatever history exists (§4.2.7; §3.7 for the HRV baseline). Where no resting-capture history exists, the readiness baselines are collected over the plan's first weeks, during which the readiness gate runs in the observe-only mode Section 3/Section 6 specify (`research/05` §3.2, step 5).

The warm start populates every determinant with a real estimate and an honest confidence; the thinner the history, the lower the confidences, and the more determinants sit at their population defaults awaiting their first qualifying efforts.

### 4.4.2 Cold start: the owned non-exercise fitness seed

Before enough running history exists to fit a critical-speed curve, the system still needs a day-one state, and `research/00` COLD-01 resolves how: seed it from a **non-exercise fitness estimate** — VO₂max inferred from HR_max, resting heart rate and demographics (`research/00` COLD-08) via an open, documented method — not the Polar OwnIndex, which `research/00` COLD-06 keeps quarantined with every output of it — and hand that seed off to the raw-data critical-speed estimate as running history accumulates. This is a **new Phase-2 requirement**: the spec must define and validate an owned cold-start estimator with its inputs, formula/parameters, and validation target (`research/00` COLD-11). Because the system *reproduces* an open method rather than reading a vendor's number, the estimator lives in the **owned/transparent namespace, not the quarantine**, and remains consistent with raw-over-derived (`research/00` PRIN-09, COLD-10).

**Inputs.** The seed uses only profile and resting-capture data that require no training history, and only the inputs of the two estimators below (`research/00` COLD-08): the estimated HR_max (§4.2.7) and `resting_hr_bpm` for the heart-rate-ratio model (`research/00` COLD-02), and age (derived from `birth_date`) and `sex` (§1.3), a body-composition term (BMI or %BF) and a self-reported activity rating (`activity_code`) for the regression model (`research/00` COLD-03), each where present. No HRV level enters the seed. Each input is optional; the estimator uses what is present and lowers confidence for what is absent.

**Formula.** The estimator combines two published, open, non-proprietary non-exercise VO₂max models, both stated here in full:

- **Heart-rate-ratio model (Uth–Sørensen form).** Resting and maximal heart rate alone give a first VO₂max estimate through the ratio relationship
  > **VO₂max ≈ 15.3 · (HR_max / HR_rest)**   (mL·kg⁻¹·min⁻¹)
  which requires only the two heart-rate anchors the profile already carries.
- **Non-exercise regression model (Jackson form).** Demographics plus a self-reported habitual-activity level give a second estimate through a linear regression of the form
  > **VO₂max ≈ β₀ + β₁·sex + β₂·age + β₃·BMI + β₄·activity_code**
  where `sex` is coded (e.g. 1 male / 0 female), `age` is in years, `BMI` is body mass over height squared, and `activity_code` is an ordinal self-reported training-habit level; the coefficients β are the published regression constants for the chosen model, carried as named parameters so the specific published model can be swapped without touching the surrounding logic.

When both models can be evaluated, the seed VO₂max is their **confidence-weighted mean** (the HR-ratio estimate weighted by the quality of the HR_rest/HR_max anchors, the regression estimate by the completeness of its demographic inputs); when only one can be evaluated, it stands alone at reduced confidence.

**From VO₂max seed to pace anchors.** The state model is expressed in velocity anchors, not in VO₂max, so the seed VO₂max is converted into a seed **vVO₂max** through an assumed running economy and then into seed **CS** and **threshold pace** through the fractional-utilization relationships:

- vVO₂max is obtained from the seed VO₂max and a default running-economy cost via the standard open running-metabolism relation `VO₂ = c · v + b_rest` inverted at VO₂max (a published metabolic-cost equation, carried with its coefficients as named parameters so a better-validated economy value can replace the default);
- seed CS and threshold pace are set as **spec-introduced default fractions of seed vVO₂max** — CS/threshold placed near the LT2 fraction of vVO₂max — with the endurance exponent held at the population `b = 1.06`. `research/01` §1.5 supplies the *sustainable-%VO₂max-by-duration* pattern that motivates a sub-vVO₂max threshold, but not the specific CS-as-fraction-of-vVO₂max value used here; that value is part of the same spec-introduced seed transform flagged below and folded under open item (1), not attributed to §1.5 as if §1.5 supplied it.

Every one of these transforms is a spec-introduced default carrying its own uncertainty, so the entire seed-derived profile is marked **low-confidence** by construction and its prediction intervals are wide.

**Validation target.** Two validation obligations attach to this estimator, discharging the `research/00` COLD-11 requirement. Offline, the chosen non-exercise VO₂max models are validated against their **published standard error of estimate** (non-exercise VO₂max regressions typically carry an SEE on the order of ~3.5–5 mL·kg⁻¹·min⁻¹; the shipped confidence interval on the seed must be no narrower than the model's own reported error). Online, the seed is validated **against the athlete's own first genuine maximal efforts** as they arrive: the hand-off period (§4.4.3) is itself the validation, and a seed that the first real efforts contradict by more than its stated interval is logged as a miss so the estimator's calibration can be reviewed. The estimator is therefore never trusted as a standalone fitness verdict; it is a day-one placeholder whose only job is to let the system produce a (wide-confidence) pace target and a starting plan before running data exists, and to be displaced by that data as fast as it accrues.

**Provenance and freedom-to-operate note.** The specific formulas above (the HR-ratio VO₂max model, the non-exercise regression, and the VO₂max→velocity transform) are **spec-introduced constructions**: `research/00` COLD-01 mandates an owned non-exercise estimator and keeps the Polar OwnIndex quarantined (COLD-06), but no captured research doc (`research/01`–`research/06`) states these particular formulas or their coefficients. They are reproduced here from the open, published non-exercise-fitness literature so an implementer needs no further lookup, and they are deliberately built from **published open models rather than any vendor's proprietary construction** — consistent with the freedom-to-operate guardrail that readiness and fitness estimates be derived from open literature, not from Firstbeat's or any competitor's protected pipeline (`research/00` FTO-01, FTO-02, FTO-03). Because this element is spec-introduced and not yet grounded in a captured research doc, it is **logged as an open item** for research back-fill (fix the specific published model and its validated coefficients) and register back-port (see the development plan); it does not block use of this section, since the cold start degrades cleanly to population defaults when its inputs are thin.

### 4.4.3 The confidence-blended hand-off

As running history accumulates, the seed-derived determinants are handed off to the raw-data running-derived estimates by the same filter that governs every other update (§4.3.1), so the transition is continuous rather than a hard switch (`research/00` COLD-01). Each running-derived observation (the first fitted CS, the first threshold effort, the first `b`-eligible spread of races) enters the filter as a high-quality observation against a low-confidence seed prior, so its gain is near 1 and it pulls the estimate strongly toward the running-derived value; within a few qualifying efforts the seed's influence has decayed to negligible and the determinant is effectively running-derived, its confidence risen accordingly. The blend is by confidence, not by a fixed schedule: an athlete who supplies several early races transitions in days, one who trains only easy for weeks stays seed-anchored longer, and in both cases the confidence label honestly tracks where the estimate actually stands. The hand-off is logged in provenance so the system can explain, at any point, how much of the current estimate is seed versus earned. Dated note 2026-10-24 (F029): as built, `b` is not handed off through the filter: it holds the population 1.06 until three tagged races, counted by their weights (2026-10-28), span a twofold GAP-equivalent distance ratio, and is then the fit of those races, switching at the bar (section 4.3.5).

### 4.4.4 Population-default fallback

When the non-exercise seed's inputs are themselves absent — no `resting_hr_bpm`, no usable demographics — the system falls back to **population defaults** with wide, honestly-flagged confidence intervals, exactly as `research/05` §3.2 originally specified: `b = 1.06`, the fractional-utilization defaults, and threshold/CS/vVO₂max left at population-typical values (or unpopulated, with the pace target carrying the maximal cold-start flag) until the first running efforts arrive. Threshold pace takes the unpopulated branch: it is estimated from tagged efforts only (section 4.3.4), no document supplies a population threshold pace, and it is served as unavailable (`no_qualifying_effort`) until the first qualifying tagged effort, in tension with `research/00` IND-03's population default (IDEA-161). This is the floor of the cold-start ladder: warm start from history where it exists, non-exercise seed where its inputs exist, population defaults where neither does — and in every case the confidence machinery of §4.3 and the guardrail-widening of §4.6 keep the system's behavior honest about how little it knows.

## 4.5 The individualization governing rule

Whether a given parameter is individualized or held at a population default is governed by one rule, resolved as the decision authority (`research/00` IND-01):

> **The system individualizes a parameter only when that parameter is both identifiable from the athlete's own data and backed by enough quality data to beat the population default; until then it holds the default with honest confidence bands rather than fitting noise.**

This resolves the tension between the warning that per-athlete fits are unstable and overfit-prone on thin field data and the warning that sophistication which does not pay off in race pace is over-engineering (`research/00` IND-01). Applied to this section's determinants, the rule **stratifies naturally** into three tiers:

- **Continuously re-anchored.** Threshold pace and the zone paces derived from it (§4.2.3) re-anchor continuously, because they are readily identifiable from ordinary training and racing and because Section 3's load chart depends on them being current. As built, threshold pace re-anchors from tagged efforts only (section 4.3.4) and is unpopulated before the first qualifying one (IDEA-161). HR_rest tracks continuously from the resting captures for the same reason.
- **Individualized once enough qualifying efforts exist.** The critical-speed profile (CS/D′), vVO₂max, and the individual endurance exponent `b` individualize only once enough qualifying maximal efforts across the required duration/distance spread exist to identify them above the noise; until then they hold their population defaults at low confidence (dated note 2026-10-24, F029: `b`'s bar is three tagged races, counted by their weights (2026-10-28), spanning a twofold GAP-equivalent distance ratio, section 4.3.5; below it `GET /state` serves the population 1.06 with `population_default` true). HR_max follows the profile's latest-file value, which can go down, and a maximal effort observed above the current estimate raises it (§4.2.7). Durability and the economy proxy are within-athlete trends by construction and are never expressed as cross-athlete-comparable absolutes (§4.2.4–§4.2.5).
- **Held fixed long-term.** The fitness/fatigue time constants (Section 3's 42/7) stay at their defaults long-term, because they are not reliably identifiable from field data and their per-athlete fitting is a later enhancement, not a launch feature (§3.5.4; `research/00` IND-06, REG-20). This tier is Section 3's, restated here only to complete the stratification the rule produces.

The rule is the single arbiter of every individualize-or-default question in the state model; a determinant is never fitted to data that cannot identify it, and a determinant that *can* be identified is never left at a default once the evidence clears the bar.

## 4.6 How low confidence widens the guardrails

Confidence is not a display-only quantity: it changes how the rest of the system behaves, discharging load-bearing finding 8 — every determinant carries a confidence, and **low confidence widens the guardrails and makes the adaptation logic more conservative** (`research/00` ARCH-11; `research/05` §3.3). Section 4 owns the confidences; the sections that consume the state model read them and respond. The concrete channels:

- **The pace target widens.** Section 1 §1.4.6 already derives the pace-target confidence band from the determinant confidences and lists cold-start state, wide endurance-exponent extrapolation, and thin/stale history as band-wideners. Section 4 supplies exactly those confidences, so a low-confidence state produces a wide, honestly-flagged pace target rather than a falsely precise one.
- **Re-anchoring is damped.** The filter gain of §4.3.1 makes a low-confidence estimate move *more* readily toward good new observations (which is desirable — it should learn fast) but also means a low-confidence determinant should not be used to justify aggressive plan changes; the adaptation logic (Section 6) is directed to treat a low-confidence determinant trend as weaker evidence for up-regulation than an equally-sized high-confidence one.
- **Up-regulation is the cautious direction.** Because low confidence makes the adaptation logic more conservative (`research/00` ARCH-11) and up-regulation is the direction Section 6 §6.7 treats cautiously, low confidence tightens specifically the *up* direction: the system may always reduce load on poor readiness regardless of state confidence, but it should not raise ambition — faster prescribed paces, bigger volume, harder key sessions — off a low-confidence determinant. A confident CS rise can justify moving the athlete's paces; a shaky one cannot.
- **Confidence is surfaced, not hidden.** The low/medium/high label travels with every determinant into the athlete-facing explanation (Section 8/9), so the athlete sees when the system is working from a provisional estimate. This is the transparency finding 8 requires and the same posture Section 1 §1.4.6 takes with the pace target.

Section 4 computes and publishes the confidences; Sections 1, 5, and 6 act on them. The division is deliberate: the state model is the single place a determinant's uncertainty is quantified, so that every consumer reads one consistent confidence rather than each re-deriving its own.

## 4.7 What this section hands to the rest of the system

Section 4 delivers the system's owned physiological state model: a profile of six determinants — critical speed and D′, vVO₂max, functional threshold pace, a within-athlete economy proxy, an emerging durability estimate, and the individual endurance exponent — plus the published HR_rest and HR_max anchors, each carrying a point estimate, a short- and long-term trend, a confidence, and a provenance stamp. Every estimate is built only from Section 3's raw-derived metrics and the athlete's own maximal efforts, never from the vendor sidecar; where the model reproduces an open method (the non-exercise cold-start seed) it is owned and stated in full. The starting state is established by a three-tier cold-start ladder — warm start from adequate history, an owned non-exercise fitness seed where its inputs exist, population defaults where neither does — with a confidence-blended hand-off that displaces the seed as running data accrues, and the whole model is governed by the single individualization rule (individualize only what the athlete's own data can identify and beat the default on) and the confidence machinery that widens the guardrails when the model is unsure.

Four explicit hand-offs carry forward. **Section 1** consumes the determinant profile at Stage 1 of its pace-target procedure — CS, D′, vVO₂max, the individual `b`, the economy modifier, the durability estimate, and any modeled acclimatization state — and derives its pace-target confidence band from the determinant confidences this section publishes (§1.4.1–§1.4.6). **Section 3** reads back the threshold-pace, HR_rest, and HR_max anchors this section owns, closing the two-way interface its load formulas depend on (§3.1, §3.4.1); every re-anchoring is version-stamped so a metric computed against a superseded anchor can be recomputed, except the HR values saved with a load: HR-TRIMP keeps the values it was computed from (§4.2.7), and threshold pace's recompute is untouched. **Section 5** anchors its relative-stored paces to the threshold/CS estimates here, targets the determinant with the largest addressable gap-to-goal (the decomposition the determinant profile enables), and supplies back the qualifying-long-run and maximal-effort definitions the state model reads to decide which sessions count as durability or CS observations. **Section 6** reads the determinant trends and — above all — the confidences, treating a low-confidence determinant as weaker evidence for up-regulation and widening its guardrails accordingly, per the finding-8 behavior §4.6 specifies. The division of labor with the neighboring sections is preserved throughout: Section 3 computes transparent metrics from raw data; Section 4 turns those metrics and the athlete's efforts into a physiological state estimate with honest confidence; Section 1 turns that estimate into the pace target the whole system optimizes.
